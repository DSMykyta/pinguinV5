# Pinguin Next — правила реалізації та розбір помилок

**Статус:** актуальні робочі правила гілки `work`, узагальнені 2026-11-10. Призначення — захистити затверджені рішення та не повторювати попередні помилки. Деталі залишаються у [конвенціях](conventions.md) і [специфікаціях компонентів](ui/overview.md).

## 1. Пріоритет рішень

1. Остання пряма вимога власника щодо конкретної поведінки переважає старе побажання, перший макет, історичні docs або припущення розробника.
2. Перед зміною звірити **актуальні** `work` HEAD, код, тести, специфікації та потрібні частини `legacy`. Якщо документація суперечлива — зафіксувати новіше затверджене рішення, не переписувати стару поведінку без підстав.
3. Гілки: `work` — розробка; `main` — production; `legacy` — вивчення історичних механік; `reserve` — резерв. Інші гілки без запиту не змінювати.
4. Ніколи не видавати «тести зелені» за «вигляд затверджено». Якщо збереглася невідповідність вимозі, вона не стає правильною через зелену CI.

**Актуальне скасування:** floating/notched labels з ранніх частин [input.md](ui/input.md) та [selection-fields.md](ui/selection-fields.md) **замінено** контрактом [field.md](ui/field.md) від 2026-11-09: постійний видимий label **над** простою рамкою, включно з search. Раніше «завжди порожній» footer тепер може містити контекстну пагінацію; історичні фрази у [universal-page-layout.md](universal-page-layout.md) не переважають [pagination.md](ui/pagination.md).

## 2. Модульність

1. `src/shell` — єдині геометрія, маршрути, панелі та контекстні слоти; `src/ui` — універсальні компоненти; `src/features` — логіка конкретного інструмента; `src/core` — загальні сервіси.
2. **Незалежність за контрактом:** UI не імпортує feature; feature не імпортує іншу feature. Передавати host, дані й callbacks через явні API. Не створювати глобальних `window.*`, прихованих event buses, DOM-discovery механізмів чи циклічних залежностей.
3. **Одне джерело істини** для даних, виділення, режиму, сортування та станів; жодних незалежних копій логіки для таблиці, плиток, редактора або вкладок.
4. `destroy`/unmount/HMR прибирає listeners, timers, observers, AbortControllers, animation frames, запити й тимчасовий DOM. Кожен екземпляр має власний lifecycle.
5. Не тягнути нові залежності чи великий фреймворк, якщо достатньо native API та чинних локальних компонентів.

## 3. Правило перевикористання — обов'язкове

**До створення будь-якого компонента перевірити наявні `src/ui`, `src/shell`, токени й legacy.** Якщо функціональність уже є — перевикористати **ту саму фабрику, DOM-контракт та CSS**, а не скопіювати стилі й назвати це повторним використанням.

- Поля — єдина рамка `src/ui/field` і відповідні Input/Select/Combobox/Listbox/Textarea/Tag/Number; label, focus, error, disabled та leading/trailing slots не дублюються.
- Режим «одне з кількох» — `src/ui/segment-switch`, `view-switch` за потреби як адаптер; не дві саморобні кнопки. Checkbox, Switch і Radio Group мають окремі native семантики.
- Menu, Dialog, Toast, RevealPanel, SelectionActions, Tooltip, IconButton, mini-button, Scrollbar та popup-positioning — лише з наявних спільних компонентів.
- Pagination — один `createPagination`; FAB — тільки `createAsideFab` із `src/shell/aside/fab.js`. Повторний екземпляр FAB допускається, **новий вигляд або незалежний FAB-компонент — ні**.
- Не створювати нових CSS-файлів варіанта у feature для зміни вигляду спільної кнопки, рамки, меню чи FAB. Feature CSS керує розташуванням власних блоків.

## 4. Shell, робоча область та анімації

1. **Один Shell, один workspace, один lifecycle вкладок.** Створення особливого режиму `fill/flush`, окремого заповнення робочої області, іншого padding або іншої анімації для вкладки **ЗАБОРОНЕНО**.
2. Tabs мають незалежні DOM-панелі/стани; «Таблиці», «Текст», «Макети даних», «Медіатека» не повинні змішувати дані або живі елементи.
3. Колекція заповнює надану область як **сам вміст**, без зайвої картки, H2, обмеження висоти чи вкладеного скролу. Текстова стаття може використовувати звичайні відступи через Page — це не workspace mode.
4. Shell уже має header, tabs, main, footer, sidebar, aside та контекстні слоти `setHeaderActions`, `setSearchContext`, `setFooterContent`, `setPageFabContext`, `setAsideContext`. **Не дублювати** header/search/footer/FAB і не втручатися в погоджену геометрію. При зміні вкладки знімати чужі контексти.
5. Зазори звіряти між **реальними видимими краями** лівої панелі/робочої області/aside. Перевіряти collapsed, docked, desktop, mobile і шапку.
6. Анімації робити спільними, стриманими і переривними, за потреби через `reveal-panel`. Hover/open/selected мають чітку індикацію. При `prefers-reduced-motion` анімація вимикається **незалежно від CSS specificity**.

## 5. Поля і загальний UI

- Нинішній стандарт: постійні видимі labels **над** 56px полем, звичайна рамка, без floating/notch, непрозорих масок чи фальшивих legend. Search із лупою; placeholder необов'язковий та не замінює label.
- Одна семантика дій: idle, hover, active, focus-visible, selected, open, disabled, error. Натиснутий або відкритий елемент має залишатися впізнаваним.
- Меню вміщує найдовший пункт **без горизонтальної прокрутки**; для наведеного, фокусованого пункту та відкритого тригера передбачений зрозумілий стан.
- Нативні input, label, button, select, dialog і табличні елементи з належними aria, keyboard/touch, кольорами й контрастом для двох тем.
- Не використовувати «готовий компонент» як формальність, якщо фактична поведінка не відповідає погодженому UI.

## 6. Таблиця, плитки, вибір і пагінація

1. Таблиця та плитки — **один набір записів**, одні sort/query/selection/page; вибір не губиться при зміні вигляду. Кожна колекція у своїй вкладці незалежна.
2. Header checkbox: якщо є **хоч один вибраний на видимій сторінці**, клік знімає вибір для всіх видимих (і з `−`, і з повного checked); якщо немає — вибирає видимі. Виділення поза сторінкою не скидати.
3. У першій клітинці — checkbox, **одразу Edit**. Меню «…» — **останній стовпець** після даних. Використовувати існуючий mini-button і Menu, не свої копії.
4. Стабільні ширини стовпців при сортуванні/пагінації, доступна горизонтальна прокрутка без обрізання, sticky table header та критичні крайові controls.
5. Групові дії — у **вже існуючому header slot**, поза flex-потоком, без зміщення пошуку, view switch чи aside toggle. Вхід/вихід через shared RevealPanel.
6. Пагінація — **в Shell footer під верхньою лінією**, а не всередині таблиці. Один paginator для таблиці та плиток, кнопки сторінок й розміри 10/25/50/100/«Усі».
7. FAB вибору кількості — **другий екземпляр тієї ж `createAsideFab`**, змонтований Shell у footer поряд із пагінацією. Перший, кутовий, залишається зі своїми діями; обидва мають **однакові** hover/open та анімації.

Документи: [collection-view.md](ui/collection-view.md), [pagination.md](ui/pagination.md), [segment-switch.md](ui/segment-switch.md).

## 7. Текстовий редактор

1. **Одна робоча область, два режими**: WYSIWYG «Редактор» та редагований вихідний «HTML». Для вибору режиму використовувати **наявний сегментований перемикач**, а не створювати дві окремі кнопки.
2. HTML з буфера в WYSIWYG має проходити очищення й вставлятися **як оформлений зміст**, якщо вставлено дійсну HTML-розмітку; в HTML-режимі залишатися кодом.
3. Не губити cursor, selection, undo/redo, IME; HTML source draft не перепарсювати на кожну клавішу. Санітизація обов'язкова на імпорті/експорті, на сервері — при зберіганні.
4. Перед «готово» перевірити `npm` imports, реальну вставку MIME `text/html`/`text/plain`, перемикання обох режимів та XSS. Не називати частковий редактор повною legacy-паритетною реалізацією.

**Додаткові регресійні вимоги редактора:**
- У WYSIWYG розрізняти `text/html` і HTML-код, скопійований як `text/plain` (із генератора, textarea чи code block). Завершені HTML-фрагменти вставляти як оформлений зміст; звичайний текст із символом `<` чи незакритим тегом не перетворювати на HTML. У режимі `HTML` вставка має залишатися кодом.
- Перевіряти вставку всередину абзацу, валідну структуру блоків/списків (без вкладення `<p>` у `<p>`), caret, selection, IME та undo/redo після переходів `Редактор → HTML → Редактор`; HTML-чернетку не санітизувати на кожному натисканні клавіші.
- Перед заявою про повну готовність перевірити справжні сценарії `text/html`, `text/plain`, rich-code clipboard, XSS, readonly, кілька ізольованих екземплярів і `destroy()`. Поточна native DOM/Range-реалізація обмежена; find/replace, check та інші legacy-шарми не є готовими без окремої реалізації.

Документи: [rich-text-editor.md](ui/rich-text-editor.md) та [research](research/rich-text-editor.md).

## 8. Процес і якість

1. Вивчити **актуальний** код + існуючі контракти + потрібний legacy; за потреби дослідити сучасні практики з **дійсно відкритими** джерелами. Не видавати неперевірені посилання за проведене дослідження.
2. **Спочатку специфікація в docs, потім код.** Чіткі API, власник стану, варіанти, edge cases, accessibility, responsive та animation; позначати відхилені/скасовані експерименти.
3. Мінімальний diff без дублювання класів, випадкових глобальних стилів і прихованих side effects. Стандарти [conventions.md](conventions.md): kebab-case, `pg-`/BEM, семантичні `--pg-` токени, CSS-власність, без `!important`.
4. Перевірити `npm run check`, `npm run test:e2e`, реальний рендер, keyboard, hover, open, дві теми, mobile, reduced motion, overflow, довгі написи і швидкі переходи. Один упалий браузерний тест — **не завершено**.
5. Комітити лише у `work`, враховувати паралельні зміни та використовувати безпечне оновлення HEAD з очікуваним SHA; ніякого force push. Новий npm-пакет підключати тільки після перевірки версій, package/lockfile, чистої інсталяції та локальної збірки. При проблемі із залежністю від'єднувати лише проблемну точку інтеграції; не відкочувати сторонні зміни. Результат задачі має бути в репозиторії, не тільки у ZIP в чаті.
6. Фінальний звіт розділяє **реалізовано / протестовано / не перевірено / залишається**. Відрізняти **написані** тести від **запущених** unit і Playwright E2E для `/tools`, Vercel `READY` від локального запуску Vite у користувача. Не називати тести успішними без реального виконання; Vercel `READY` не доводить наявності npm-пакетів на комп'ютері власника.
7. Нові записи про користувача в персональну пам'ять **не створювати без прямого запиту**. Цей файл — документація репозиторію, не пам'ять.

## 9. Помилки асистента — ретроспектива (останній розділ)

Наведені факти відтворено з повідомлень власника, тестів та поточних файлів; це **не** твердження про повний аудит усіх комітів.

1. **Shell:** робив різні відступи зліва/справа, неправильний зазор між aside і полотном, зсув у шапці замість спільної геометрії.
2. **Вкладки:** спочатку «Таблиці» та «Текст» фактично використовували не повністю відокремлені робочі області.
3. **Toast:** недостатньо підтримав кілька одночасних повідомлень і плавне закриття; картка смикалася/зникала замість повного виїзду вниз.
4. **Dialog:** потребував кількох подальших виправлень контрастності кнопок у темах.
5. **Input:** перша floating-label реалізація впала на тесті reduced motion через пріоритет CSS; після кількох невдалих floating/notch експериментів погоджено статичний Field. Раніше я назвав дизайн завершеним до остаточного візуального погодження.
6. **Колекція:** додавав непотрібні заголовки, картки, внутрішній скрол і **заборонений** спеціальний `fill/flush` workspace, а також іншу анімацію для «Макетів даних».
7. **Перемикачі:** малював окремі кнопки або альтернативний вигляд там, де треба було перевикористати legacy-подібний segmented switch.
8. **Таблиця:** header checkbox зі змішаним `−` не знімав уже обране; невірно розміщував Edit/menu, через що довелося переробляти порядок контролів.
9. **Меню:** недостатній стан hover/open, обмежена ширина і зайва горизонтальна прокрутка.
10. **Пагінація:** спершу створив не той вигляд і розмістив не у штатному footer під лінією.
11. **FAB:** замість **перевикористання** існуючої фабрики зробив новий вигляд/механіку; далі окремо виправляв вирівнювання й hover.
12. **Rich Text Editor:** спочатку віддав ZIP у чат замість інтеграції в `work`; **двічі** зробив дві паралельні колонки WYSIWYG + mirror замість однієї області з перемикачем «Редактор / HTML». Додав Tiptap/`dompurify` без забезпеченої локальної інсталяції — Vite показав `Failed to resolve import`; відкат тимчасово залишив проєкт без редактора. Не перевірив HTML як `text/plain`, тому в режимі редактора показувалися буквальні `<p>`, `<strong>`, `<li>`. Створив власні кнопки режимів замість спільного `createSegmentSwitch()`.
13. **Процес:** рано писав, що все готово, не дочекавшись перевірок усіх сценаріїв; інколи робив зайву реалізацію замість мінімального повторного використання. Плутав успішну збірку Vercel, ізольовані перевірки та доведену роботу всього редактора в локальному браузері; заявляв про готовність до відтворення повної механіки legacy.
14. **Документація:** залишив суперечливі історичні описи labels, workspace, footer та FAB, не позначивши достатньо явно пріоритет нових вимог. Створив дубль правил у `docs/implementation-rules.md`, хоча вже існували `project-rules.md` та `approved-ui-rules.md`; замість цього слід було доповнити зведений документ.

**Відомі невиправлені розбіжності станом на перевірку 2026-11-10:** `src/ui/rich-text-editor/mode.js` усе ще має дві власні кнопки замість композиції shared `createSegmentSwitch`; `src/ui/field/field.css` усе ще містить `!important` для reduced motion попри заборону в конвенціях; кілька старих розділів `docs/ui/overview.md`, `docs/ui/input.md` та layout/collection docs лишаються архівними. Цей документ **лише фіксує** ці невідповідності, не видає їх за вже виправлений код.

Перелік охоплює помилки, доступні для перевірки з цього контексту, але не гарантує відсутності інших дефектів.
