# Pinguin Next — правила шапок файлів

**Статус: обов'язковий контракт для гілки `work`.** Повноцінна шапка має бути у кожному власному `.js`, `.mjs`, `.css`, `.html`, `.yml` та `.yaml` файлі. Правило поширюється на `src`, `scripts`, `tests`, конфігурацію Playwright, `index.html` та робочі процеси GitHub Actions.

## 1. Що обов'язково має бути в шапці

1. **PINGUIN NEXT — назва сутності**: її справжня роль, а не вигаданий чи застарілий модуль.
2. **ПРИЗНАЧЕННЯ**: що саме реалізовано у файлі.
3. **ЗАЛЕЖНОСТІ**: конкретні імпорти, зовнішні або спільні модулі; якщо немає — так і написати.
4. **ПУБЛІЧНИЙ API**: реальні експорти, CSS-класи, команда запуску, тестовий набір або «Немає» для внутрішнього файлу.
5. **ПРИНЦИП**: важлива межа відповідальності та правило перевикористання, не загальна фраза.
6. **Коробка `╔ ╠ ╚`**: єдине зрозуміле оформлення на початку файлу, як у `src/ui/button/button.js`.

Значення **не можуть бути вигаданими**. Перевіряй назви API, імпорти та межі відповідальності після будь-якого рефакторингу. За довгих рядків переносити текст на нові рядки всередині коробки, не ламати вирівнювання.

## 2. Приклад для JavaScript

```js
/**
 * ╔══════════════════════════════════════════════════════════════════╗
 * ║ PINGUIN NEXT — VIEW SWITCH                                       ║
 * ╠══════════════════════════════════════════════════════════════════╣
 * ║ ПРИЗНАЧЕННЯ: Адаптер режимів перегляду над segment-switch.        ║
 * ║ ЗАЛЕЖНОСТІ: src/ui/segment-switch/segment-switch.js.             ║
 * ║ ПУБЛІЧНИЙ API: createViewSwitch().                                 ║
 * ║ ПРИНЦИП: Відповідальність за збереження належить викликачу.       ║
 * ╚══════════════════════════════════════════════════════════════════╝
 */
```

Для CSS застосовується звичайний `/* ... */` з тими самими полями. У полі API — клас чи набір класів компонента, а не вигадані JavaScript-функції. Для тестів поле API описує тестовий набір та спосіб запуску. Для скрипта із shebang шапку розміщують одразу після першого рядка `#!/...`. Для HTML зберігають `<!doctype html>` першим рядком, а далі розміщують шапку у `<!-- ... -->`. Для YAML коробку формують рядками-коментарями `# ...`.

## 3. Винятки та заборони

- `.json`, `.md`, `.gitignore`, `.editorconfig` не отримують коментарів, несумісних зі своїм форматом; Markdown уже має власні заголовки.
- Не замінювати інформаційну шапку одним-двома рядками `/** ... */`.
- Не копіювати шапку з іншого компонента без перевірки призначення та API.
- Не додавати другу коробку поруч з уже наявною; підтримувати **один** канонічний коментар.
- Не послаблювати перевірку заради проходження CI. Нові винятки потребують обґрунтування й оновлення цього документа.

## 4. Контроль

`npm run check:headers` перевіряє наявність повної структурованої шапки на початку кожного контрольованого файлу. `npm run check` запускає цю перевірку разом із неймінгом, тестами та збіркою; GitHub Actions виконує `npm run check` для `work` і PR до `main`.

**Автоматичний контроль гарантує структуру, але не перевіряє правдивість опису.** Залежності, API та архітектурні принципи мають перевірятися під час review.
