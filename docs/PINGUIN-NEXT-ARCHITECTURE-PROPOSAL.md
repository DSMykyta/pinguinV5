# Pinguin Next — архітектурний концепт (чернетка для обговорення)

**Статус:** proposal, **не** затверджено для реалізації. Дата: 2026-11-05.
**Гілка:** \`work\`. \`main\` і \`reserve\` не змінюються цим документом.

## 1. Чому не робити просто ще один CSS-ремонт

У поточному \`main\` є багатосторінковий Vite-застосунок, велика HTML/CSS/JS система, зовнішні інтеграції Google Sheets/Drive, окремі Vercel Functions, гнучкі генератори, редактор, табличні компоненти, авторизація, модальні вікна, навігація і контекстні aside.
Інвентаризація Git tree: **845 елементів** (із них 754 файли), **432 JS-файли**, **91 CSS-файл**, **64 файли шаблонів**, **24 елементи API-дерева** (файли й каталоги).

Багато модульних ідей уже правильні. Документ \`docs/PROJECT-OVERVIEW.md\` описує: (1) один файл — одна роль, (2) плагіни не імпортують один одного, (3) збій плагіна не повинен падати на весь застосунок. Ці принципи залишаються основою.

Проблема не лише в кількості файлів, а в неоднорідності контрактів, історичних шарах, подвоєнні механізмів, підключенні UI через неявні атрибути/глобальний DOM, загальному \`main-core\` та можливості неузгодженості між окремими частинами. Не кожен великий файл автоматично поганий; важливі відповідальність, тестованість і явні межі.

## 2. Ідея продукту

**Pinguin — особистий універсальний workspace для роботи й творчості.** Не «набір окремих html-сторінок», а стабільна оболонка з підключуваними інструментами.

- Ліва навігація: групи інструментів, активний модуль, пошук/швидкий перехід.
- Центральна частина: простір активної задачі, не багато декоративних карток.
- Правий aside: тільки контекст поточного інструмента; не обов'язковий для кожного екрана.
- Світла, темна й системна теми, без ефектів заради ефектів.
- Стабільні однакові контроли: input, select, table, menu, modal, toast, confirmation.
- Робочі (products, mapping, text, tables, images) та творчі/ігрові модулі можуть співіснувати, не прив'язуючись один до одного.

Референс: ієрархія, компактність і поведінка ChatGPT, **не** перенесення недокументованих класів CSS/фірмових активів.

## 3. Три постійні Git-гілки

| Branch | Роль | Деплой |
|--------|------|--------|
| \`main\` | Опублікована перевірена версія | Production через Vercel |
| \`reserve\` | Знімок попереднього стабільного \`main\` | Не production, не прямі розробки |
| \`work\` | Нова архітектура / один модуль за раз | Preview через Vercel |

**Публікація:** закінчити модуль у \`work\` → перевірити CI й Preview → зафіксувати поточний SHA \`main\` у \`reserve\` → створити/оновити PR \`work\` → \`main\` → після схвалення злити → перевірити Production → синхронізувати \`work\` з \`main\`.

Не міняти імена/призначення гілок; не робити \`force push\` в \`main\`; не переносити експериментальні зміни в production без проходження контрольних перевірок. Якщо \`work\` не готова вся — не зливати.

**Відкат:** повернути код із SHA попередньої версії або зробити Git revert релізу, який запускає коректний Production deploy; Vercel rollback можна використати для швидкого відновлення сайта. Відновлення коду **не відновлює** автоматично Google Sheets/Drive — для даних потрібні окремі резерви.

## 4. Архітектурні правила (контракт)

1. **Одна відповідальність на модуль/файл**, але не розрізати 20 рядків на 10 файлів без реальної потреби.
2. **Модулі-функції не імпортують код інших функцій**. Вони спілкуються через публічні події / сервіси з описаними контрактами.
3. **Кожен модуль автономний**: вимкнення, видалення чи збій не знищує оболонку й не ламає інші модулі.
4. **Немає прихованої ініціалізації** через випадкові CSS-селектори, \`window.*\`, порядок вставки скриптів або сторонні побічні ефекти.
5. **Одне джерело істини** для глобальних токенів дизайну, роутингу, конфігурації модулів і доступу до API.
6. **API і дані — окремо від інтерфейсу.** Можна підставити мок-джерело без мережі та не торкатися робочих Google Sheets.
7. **Усі операції мають завершені стани**: loading, empty, error, success, permission denied.
8. **Плагін обробляє помилку локально, але не приховує її**: UI показує збій і відновлення; журнал/тести фіксують помилку.
9. **Accessibility**: клавіатура, фокус, зрозумілі підписи, контраст, доступність без анімації.
10. **Одна функція = одна закінчена вертикальна робота:** інтерфейс, дані, поведінка, тести, документація та перевірка перед переходом до наступної.

## 6. Як перейти зі старого застосунку

**Не переписувати весь сайт за один PR.** \`main\` працює як зараз; у \`work\` створюється новий \`src/\`. Стара реалізація залишається джерелом перевіреної логіки та еталоном очікуваного результату, але не «джерелом дизайну».

- Етап 0: угода про архітектуру й маршрут міграції; ніяких зламаних функцій.
- Етап 1: UI shell + дизайн-токени + системна навігація/контекстний aside + теми (без фейкових кнопок).
- Етап 2: перша мала **працююча** фіча «Текст»: ввід, лічильники, копіювання/очищення, стани, unit + interaction tests.
- Етап 3: відділення генераторів таблиць і обробки зображень, кожен окремим завершеним кроком.
- Етап 4: сервісний шар API/Auth/Sheets/Drive з моками й тестовими даними.
- Етап 5: каталоги/товари/мапінг/бренди та інші залежні модулі по одному.
- Етап 6: творчі/ігрові модулі за тими самими контрактами.

Порядок після оболонки — пропозиція; його уточнювати за реальним пріоритетом користувача. Доки кожна важлива стара функція не мігрована та не перевірена, не видаляти її код.

### Критерій готовності функції

- Має зрозумілий сценарій і межі відповідальності.
- Можна увімкнути/вимкнути без редагування інших модулів.
- Не чіпає недокументовані глобальні змінні та реальні робочі дані у Preview.
- Усі дії реально працюють; немає декоративно-неактивних кнопок.
- Перевірені порожні, успішні, помилкові й асинхронні стани.
- Тести й збірка проходять; є ручна перевірка у Vercel Preview.
- Не погіршує доступність, вузькі екрани та темні режими.

## 8. Важливі ризики

- Історія Git — це **код**, а не резервна копія даних Google Sheets/Drive. Окремо захистити дані й права доступу.
- Preview з однаковими секретами може працювати з реальними даними. Для перевірок потрібні sandbox/mock дані та недоступність шкідливих записів у Production.
- Не копіювати 1.6 MB зібраного CSS ChatGPT із папки \`GPT CSS/\`: в новій системі потрібні свої компактні design tokens.
- \`main\` зараз не має branch protection; рекомендовано вимагати успішний CI та PR-рев'ю для публікацій.
- Не робити \`force push\` в \`main\`, не переставляти production branch при кожному релізі.
- **Перевірено 2026-11-05:** у GitHub `delete_branch_on_merge = true`. Перед першим PR із постійної гілки `work` його треба вимкнути в Settings → General → Pull Requests, інакше GitHub автоматично видалить `work` після merge.
- **Перевірено 2026-11-05:** `main` має `protected = false`; налаштувати ruleset/required checks перед релізним процесом.
