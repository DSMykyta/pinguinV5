# Правила реалізації, перевірки та передачі змін — Pinguin Next

**Статус:** обов'язкове доповнення до [канонічних конвенцій](conventions.md) для гілки `work`. Дата фіксації: 2026-11-10. Підстава — розробка нового редактора та зауваження до повторного використання компонентів.

Цей документ не замінює `docs/conventions.md` і не дозволяє змінювати затверджену архітектуру без узгодження. Його завдання — визначити **порядок роботи, критерії перевірки та конкретні заборони**, які запобігають уже допущеним помилкам. Якщо правила суперечать чинному контракту компонента, спочатку зафіксувати суперечність та погодити її; не вводити приховану альтернативну архітектуру.

## 1. Джерело завдання та межі змін

1. **Працювати з фактичним проєктом.** Для Pinguin Next ціль — `DSMykyta/pinguinV5`, гілка `work`. `main`, `legacy` та `reserve` не змінювати. Не вважати назву продукту або архів із чату шляхом до робочого репозиторію.
2. **Результат — у репозиторії.** Коли просять дослідити, задокументувати й реалізувати компонент, створити/оновити файли у відповідних `docs/`, `src/`, `tests/`, а не заміняти інтеграцію ZIP-файлом або фрагментом коду в чаті.
3. **З'ясувати семантику до реалізації.** Якщо назва на кшталт «дзеркальний редактор» допускає різні механіки, порівняти її з явною поведінкою `legacy`, наявними контрактами та прикладами користувача. Не обирати альтернативний UI через те, що він здається сучаснішим.
4. **Не розширювати обсяг непомітно.** Не додавати непрохані панелі, режими, FAB, сторінки, дизайнерські варіанти, автозбереження або можливості, які користувач не затвердив. Демонстрацію розміщувати лише у відведеній робочій області.
5. **Зберігати незалежні незавершені зміни.** Перед записом читати актуальний `work`; коміт формувати поверх поточного SHA і оновлювати ref тільки з перевіркою очікуваного SHA (без `force`). Змінювати мінімальну множину файлів. Не відкотити чужі коміти через локальну помилку одного модуля.

## 2. Дослідження до коду

1. Перевірити три джерела: **реальний сценарій користувача**, **наявний код Pinguin Next**, **механізм `legacy`**. Окремо оцінити сучасні підходи, але не копіювати їхню UI-стилістику чи API без потреби.
2. Писати в `docs/ui/<component>.md` призначення, поведінку, API, модульні межі, відомі обмеження й критерії приймання. Глибоке порівняння розміщувати в `docs/research/`; короткий реєстр — у `docs/ui/overview.md`.
3. Переносити **функцію та очікувану взаємодію**, а не весь старий HTML, CSS, глобальні хендлери або `document.execCommand()`. Legacy — джерело вимог, не готова нова архітектура.
4. Кожна функція має мати визначену відповідальність і тестований контракт; дослідження та документ не вважати реалізацією.

## 3. LEGO-модульність і повторне використання

1. **Пошук перед створенням:** перевіряти `src/ui`, `src/core` і відповідні документи. Якщо вже є `createSegmentSwitch`, `createIconButton`, `createMenu`, `createPagination`, `createTextarea`, `createPageView`, `createTabs`, Shell FAB або слот contextual actions — **перевикористати** їхній API. Не малювати аналог у feature чи новому UI-модулі.
2. Розвивати існуючий спільний компонент через параметр/композицію, тільки коли сценарій справді спільний. Не дублювати код лише для того, щоб візуально повторити стиль.
3. `src/ui` не залежить від `src/features` і `src/shell`; окремі адаптери одного компонента не імпортують один одного. Власник композиції передає мінімальний `controls`/callbacks. Кожен адаптер звільняє listeners, observers, таймери та DOM через `dispose()`/`destroy()`.
4. Не створювати глобальний стан, `window.*` API, друге незалежне джерело істини або другий життєвий цикл для тієї самої взаємодії.
5. CSS компонента належить лише йому; класи `pg-*`, BEM, семантичні `--pg-*` токени, правильні focus/hover/selected/disabled стани, світла і темна теми. Feature CSS розміщує компоненти, але не перевизначає їхній вигляд.
6. **Одна Shell-геометрія.** Заборонено окремі режими `fill/flush` для робочої області, нову анімацію тільки для однієї вкладки, дублікати header, aside, toolbar-зон, FAB, пагінації чи вкладок. Таблиці та контент використовують спільні конструкції, передбачені чинними `docs/universal-page-layout.md` та `docs/ui/collection-view.md`.
7. Компонент залишається доступним із клавіатури, читабельним для скринридера, на вузькому екрані та з `prefers-reduced-motion`. Натиснутий стан відрізняється від hover; контроли не обрізаються контейнером без реальної необхідності.

## 4. Обов'язковий контракт редактора «Редактор / HTML»

1. **Одна робоча поверхня й один логічний документ.** Режим `editor` — візуальне редагування; режим `html` — редагування вихідного коду **на тому самому місці**. Два одночасно видимі стовпці `editor + mirror` не відповідають цій вимозі.
2. Перемикач режимів має бути наявним **спільним `src/ui/segment-switch`**, а не новим набором стилізованих кнопок. Ця інтеграція **ще не виконана** в поточному редакторі; вважати відкритим дефектом повторного використання.
3. Під час переходу `editor → html` код отримується з актуального оформленого документа. Під час `html → editor` застосовується редагована HTML-чернетка після дозволеної нормалізації; змінений документ не губиться.
4. **Не переписувати HTML textarea при кожному натисканні клавіші**: зберігати нативний caret, виділення, IME/композицію, undo/redo і текст незавершеної розмітки. У візуальному редакторі не руйнувати виділення та історію форматування.
5. Поведінка вставки залежить від **цільового режиму** і **формату буфера**:
   - У `html` будь-який скопійований код залишається буквальним редагованим кодом.
   - У `editor` справжній `text/html` проходить очищення та вставляється як оформлений вміст.
   - У `editor` повний HTML-фрагмент у `text/plain` (зокрема скопійований як код або з code block) розпізнається й відображається оформленим; неповний текст із символами `<` не повинен довільно ставати розміткою.
   - Після вставки мають працювати зміна режиму, історія, виділення, вставка в середину абзацу й списки. Не вкладати блокові теги всередину `<p>`.
6. HTML не запускати як JS і не переносити небезпечні елементи, `on*` обробники чи небезпечні URL. Клієнтське очищення — **не** заміна серверної валідації при збереженні й публікації.
7. Незалежні можливості (formatting, history, paste, stats, майбутні find/replace, check, cleanup) підключаються за контрактом, без взаємних імпортів. Не оголошувати відсутні «шарми» реалізованими.
8. Поточне `contenteditable` + DOM Range рішення **не є повним аналогом ProseMirror/Tiptap**. Для складних вкладених структур потрібні окреме рішення та тести; не маскувати технічні обмеження.

## 5. Залежності та захист запуску сайту

1. **Жодного імпорту неінстальованого пакета.** Якщо бібліотека справді потрібна, перевірити її версію, наявність у `package.json` і lockfile, успішне встановлення та `npm run check` у чистому середовищі **до** імпорту з головного entrypoint.
2. Не додавати Tiptap, DOMPurify, CodeMirror чи інший пакет лише за назвою. Нове рішення має працювати на локальному `npm run dev`, а не тільки на CI, який сам установлює залежності.
3. Не підключати експериментальний або неготовий модуль як безумовний імпорт із `src/main.js`/активної feature. Спочатку перевірити ізольовано; якщо модуль опційний, використовувати контрольоване підключення без ризику для всього Shell.
4. При аварії виправити/відключити **точку інтеграції**, зберігши інші робочі зміни. Не приховувати помилку Vite вимкненням overlay — виправляти причину.
5. Після rollback прямо вказати, що функцію прибрано й завдання не завершено; не називати відкат готовим редактором.

## 6. Перевірки, які не можна підміняти одна одною

| Рівень | Що перевіряє | Дозволене твердження |
| --- | --- | --- |
| Статичний огляд / лінтер / неймінг | структуру файлів, конвенції, прості помилки | «Статичні перевірки пройшли» |
| `node --test` | ізольовану JS-логіку | «Модульні тести пройшли» |
| `npm run build` або Vercel `READY` | збірку конкретного коміту у **своєму** середовищі | «Збірка пройшла»; не «у тебе все працює» |
| Playwright E2E на `/tools` | інтеграцію, DOM, фокус, ввід, режими, локальну поведінку | «E2E сценарії, що реально запускалися, пройшли» |
| Локальний `npm run dev` + браузерний перегляд | розробницький сервер, користувацький сценарій та візуальну відповідність | «Перевірено локальний запуск» — **лише якщо його справді виконано** |

Перед заявою про готовність перевірити: старі сторінки і вкладки; обидва режими; raw HTML paste та rich clipboard; undo/redo; роботу IME і caret; небезпечний HTML; readonly; кілька екземплярів; destroy; клавіатуру; мобільну ширину; теми; відсутність overflow. Тестові файли, які **лише написані**, не зараховуються як виконані тести.

Якщо доступ до локального комп'ютера чи реального браузера відсутній, **явно написати «не перевірено»**. Не змішувати результат standalone fixture, unit-тестів і E2E всього сайту. Не замовчувати відкриті дефекти.

## 7. Порядок виконання та критерій завершення

1. Зафіксувати завдання: очікуваний UX, межі, скриншоти/legacy, конкретні сценарії приймання.
2. Перевірити наявні компоненти, документи, гілку та точку інтеграції. Виявити можливе перевикористання.
3. Записати короткий контракт у `docs/ui` і дослідження у `docs/research` — **перед кодом**.
4. Реалізувати лише потрібні незалежні частини; підключити їх у потрібну робочу область, не змінюючи Shell.
5. Додати unit та E2E із **реальним** сценарієм користувача, регресіями та небезпечними випадками.
6. Запустити доступні перевірки, зафіксувати, що запускалося, а що ні; не підміняти браузерний тест Vercel `READY`.
7. Комітити мінімальний набір файлів у `work`, перевірити diff, стан гілки, результат збірки і відсутність змін у `main`.
8. Повідомити стисло: **що реально працює, який коміт, що перевірено, що ще не готово**. Не переносити основний результат у ZIP у чат.

**«Готово» означає не «код існує», а «завдання відповідає вимозі, інтегроване, не ламає інші сценарії, потрібні тести реально виконані»**. За неповної перевірки — «реалізовано, перевірка не завершена».

**Мій основний системний збій:** я кілька разів починав із власного технічного рішення, а не з перевіреного сценарію користувача та вже існуючих компонентів; після цього переоцінював доказовість збірки/часткових тестів. Надалі пріоритет: **правильна механіка → повторне використання → безпечна інтеграція → перевірка → точний звіт**.
